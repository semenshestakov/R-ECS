# Сущности и представления

[🇬🇧 English](../../en/guides/entities-and-views.md) · [⬆ Документация (RU)](../README.md)

Всё, что касается сущностей, идёт через `registry.Entities()`, который
возвращает [`ecs::EntitiesManager`](../api/index_classes.md).

## Создание и уничтожение

```cpp
auto& world = registry.Entities();

ecs::EntityWrapper e = world.Create(prefab);  // собрать из префаба
bool alive = e.IsAlive();                      // true

e.SelfDestroy();                               // уничтожить через обёртку
// или: world.Destroy(e.getEntity());
```

`ecs::Entity` — крошечный хэндл `{id, version}`. Версия увеличивается при
переиспользовании id, поэтому устаревший хэндл на уничтоженную сущность вернёт
`IsAlive() == false`, а не молча «попадёт» в новую сущность.

## EntityWrapper — безопасный хэндл

`Create` возвращает [`ecs::EntityWrapper`](../api/index_classes.md): сущность
плюс ссылку на её менеджер, так что действовать можно напрямую.

```cpp
e.GetComponent<Position2d>().x = 5.f;          // ассерт: компонент существует

if (auto* hp = e.TryGetComponent<Health>())    // nullptr, если нет / мертва
    hp->value -= 10.f;

ecs::entityId_t id = e.getId();
```

`GetComponent<T>()` ассертит, что сущность жива и владеет `T`;
`TryGetComponent<T>()` возвращает указатель (или `nullptr`) и не ассертит.

## Итерация через представления (views)

`view<Components...>()` выдаёт только сущности, владеющие **всеми**
перечисленными компонентами. Каждый шаг итерации разбирается на ссылки, которые
можно читать и менять на месте.

```cpp
for (auto [pos, vel] : world.view<Position2d, Velocity2d>())
{
    pos.x += vel.x;        // ссылки в хранилище — записи сохраняются
    pos.y += vel.y;
}
```

Поскольку сущности сгруппированы по архетипам в плотных чанках, представление
идёт по непрерывной памяти — это кэш-дружелюбное ядро фреймворка. Представление
с одним компонентом работает так же:

```cpp
for (auto [hp] : world.view<Health>())
    if (hp.value <= 0.f) { /* пометить на удаление */ }
```

### Получение хэндла сущности

Только **первый** аргумент (`Head`) выбирает хэндл, который выдаётся рядом с
компонентами; все последующие аргументы — это компоненты (или теги-фильтры, см.
ниже). Поставьте `Entity` первым, чтобы дополнительно получать хэндл владеющей
сущности первым элементом каждого шага. `Entity` не является компонентом — он
исключается из фильтра по архетипу, поэтому представление по-прежнему отбирает
сущности только по остальным компонентам:

```cpp
for (auto [entity, pos, vel] : world.view<Entity, Position2d, Velocity2d>())
{
    pos.x += vel.x;
    if (pos.x > bound) world.Destroy(entity);   // хэндл уже на руках, без лишнего поиска
}
```

`view<Entity>()` сам по себе обходит все живые сущности и выдаёт только их хэндлы.

Представление выдаёт **ровно один** хэндл, выбираемый головой. Поставить второй
хэндл после головы — ещё один `Entity` или любой тип `EntityWrapper` — это
**ошибка компиляции**:

```cpp
world.view<Entity, Position2d, Player>();   // ошибка: Player — хэндл, а не компонент
world.view<Frozen, Entity>();               // ошибка: Entity допустим только как голова
```

Головой можно поставить и тип-обёртку, чтобы получать её вместо «сырого»
`Entity` (см. [Типизированные обёртки](#типизированные-обёртки)). `EntityWrapper`
наследует от `ecs::Tag`, поэтому **именованный** наследник обёртки сам является
тегом и фильтрует по своему биту: `view<Player, Health>()` выдаёт `Player` только
для сущностей, у которых есть тег `Player` **и** компонент `Health`. Единственное
исключение — базовый `EntityWrapper`: он исключён из концепта тега, поэтому
`view<EntityWrapper, Health>()` не добавляет фильтра и выдаёт обёртку для каждой
сущности, владеющей `Health`.

### Опциональные компоненты

Запишите компонент как указатель — `Component*` — чтобы сделать его
опциональным. Опциональные компоненты **не** участвуют в фильтре по архетипу:
представление по-прежнему отбирает сущности по обязательным (не-указательным)
компонентам, а для каждого совпадения опциональный аргумент выдаёт указатель на
компонент, если сущность им владеет, иначе `nullptr`. Это аналог
`TryGetComponent` на этапе итерации:

```cpp
for (auto [pos, vel] : world.view<Position2d, Velocity2d*>())
{
    pos.x += 1.f;                    // Position2d обязателен — ссылка
    if (vel) pos.x += vel->x;        // Velocity2d опционален — указатель или nullptr
}
```

Маркеры сочетаются с `Entity` и друг с другом:

```cpp
for (auto [entity, hp, shield] : world.view<Entity, Health, Shield*>())
    ...
```

Если все перечисленные компоненты опциональны, обязательный фильтр пуст и
представление обходит все живые сущности, сообщая для каждого опционального
компонента его наличие или `nullptr`.

### Чтение нескольких компонентов сразу

`GetComponents<...>()` применяет те же правила `Component` / `Component*` к одной
сущности по хэндлу, возвращая кортеж вместо итерации. Обязательный `Component`
возвращается ссылкой, опциональный `Component*` — указателем (`nullptr`, если
компонента нет). Это пакетный аналог `GetComponent` / `TryGetComponent`:

```cpp
auto [pos, vel] = world.GetComponents<Position2d, Velocity2d*>(entity);
pos.x += 1.f;
if (vel) pos.x += vel->x;
```

## Теги

**Тег** — это маркер нулевого размера, наследующий от `ecs::Tag`. Он участвует в
архетипе сущности — занимает бит, — но **не хранит данных** на сущность, так что
колонка в чанке для него никогда не выделяется. Теги — это чистые фильтры.

```cpp
struct Frozen final : ecs::Tag {};
struct Boss   final : ecs::Tag {};
```

Навешивайте теги при сборке префаба через `AddTag<T>()` либо на живую сущность
через `AddTag<Tags...>()` / `RemoveTag<Tags...>()` у менеджера. Как и
`AddComponents`, они переносят сущность в новый архетип, но не конструируют
данных; для мёртвой сущности это no-op, а добавление уже имеющегося тега ничего не
делает:

```cpp
prefab.AddTag<Frozen>();               // на префабе

world.AddTag<Frozen, Boss>(entity);    // на живой сущности
world.RemoveTag<Frozen>(entity);
```

Проверить, несёт ли живая сущность тег, можно через `HasTag<T>()` — это тег-аналог
`TryGetComponent`: раз у тега нет данных, возвращать нечего, кроме bool. Метод
доступен и у менеджера, и, для удобства, у `EntityWrapper`; оба возвращают `false`
(без ассерта) для мёртвой сущности:

```cpp
bool frozen = world.HasTag<Frozen>(entity);   // у менеджера
bool frozen2 = wrapper.HasTag<Frozen>();      // у хэндла EntityWrapper
```

У каждого есть низкоуровневый, нешаблонный аналог, принимающий componentId_t
в рантайме вместо типа тега на этапе компиляции — то же разделение, что у
`GetComponent<T>` / `GetComponentData(componentId)`:

```cpp
bool frozen3 = world.HasTagById(entity, ComponentRegistrator::GetComponentId<Frozen>());
bool frozen4 = wrapper.HasTagById(ComponentRegistrator::GetComponentId<Frozen>());
```

В `view` теги везде **только фильтруют**: они дают бит в архетипе, но никогда не
выдаются и не выделяют колонку. Чистый тег, поставленный головой, всё равно выдаёт
`Entity`:

```cpp
for (auto [entity] : world.view<Frozen>())            // тег-голова -> выдаёт Entity, фильтрует по Frozen
    ...

for (auto [pos] : world.view<Position2d, Frozen>())   // Frozen фильтрует; выдаётся только Position2d
    ...

// Складывайте теги, чтобы сузить запрос:
for (auto [entity, pos] : world.view<Entity, Position2d, Frozen, Boss>())
    ...                                               // frozen И boss
```

### Теги-обёртки

`EntityWrapper` наследует от `ecs::Tag`, поэтому **любой именованный наследник
обёртки уже является тегом** — отдельный базовый класс не нужен. Поскольку
`ecs::Tag` пуст, он схлопывается оптимизацией пустого базового класса (EBO), так
что обёртка остаётся `sizeof(EntityWrapper)` и по-прежнему удовлетворяет
`EntityWrapperLike`. Головой представления именованная обёртка делает **оба** дела:
выдаёт обёртку *и* фильтрует по своему биту. Навешивайте этот бит как обычный тег —
через `AddTag<Door>()`.

```cpp
struct Door final : ecs::EntityWrapper           // именованная обёртка — уже тег
{
    using EntityWrapper::EntityWrapper;
    Position2d& GetPosition() { return GetComponent<Position2d>(); }
};

prefab.AddTag<Door>();                            // пометить сущность как Door

for (auto [door] : world.view<Door>())           // выдаёт Door, фильтрует по биту Door
    door.GetPosition().x += 1.f;
```

Сравните виды головы-хэндла: базовый **`EntityWrapper`** выбирает хэндл-обёртку, но
не добавляет фильтра; **чистый тег** (`Frozen`) выдаёт `Entity` и фильтрует;
**именованная обёртка** (`Door`, `Player`) выдаёт эту обёртку и фильтрует по своему
биту.

> Поскольку именованная обёртка теперь фильтрует по своему тегу, сущность попадёт в
> `view<Door>()` только когда действительно несёт тег `Door` (через `AddTag<Door>()`
> на префабе или живой сущности). `Create<Door>(...)` возвращает хэндл `Door`, но
> сам бит не выставляет.

### Осмотр архетипа сущности

`GetArchetype(entity)` возвращает константную ссылку на архетип сущности — её
«отпечаток» набора компонентов. Проверяйте принадлежность по id компонента; это
работает и для компонентов, и для тегов:

```cpp
const ecs::Archetype& arch = world.GetArchetype(entity);
bool frozen = arch.test(ecs::ComponentRegistrator::GetComponentId<Frozen>());
```

Для одного тега вместо `GetArchetype` + `test` лучше использовать `HasTag<T>(entity)`
— та же проверка, но напрямую и безопасно для мёртвой сущности (см. выше).

Ссылка остаётся валидной, пока сущность не мигрирует (любое добавление/удаление
компонентов или тегов) или не будет уничтожена. `GetArchetype` ассертит, что
сущность жива.

Чтобы получить *все* теги или *все* компоненты сущности разом, а не проверять по
одному, используйте `GetTagIds(entity)` / `GetComponentIds(entity)`. Оба метода
пересекают архетип с общей на весь процесс маской из `ComponentRegistrator` (одна
маска — все зарегистрированные id тегов, другая — все id компонентов с данными) и
возвращают результат как обычный `collections::BitSet` — разовый снимок, а не
зарегистрированный архетип: у него нет хеша, и он не привязан к хранилищу:

```cpp
for (ecs::componentId_t id : world.GetTagIds(entity))
    ...                                    // каждый бит тега у сущности

for (ecs::componentId_t id : world.GetComponentIds(entity))
    ...                                    // каждый бит компонента с данными
```

Оба метода, как и `GetArchetype`, ассертят, что сущность жива.

## Изменение набора компонентов сущности

`AddComponents` и `RemoveComponents` переносят сущность в новый архетип,
сохраняя значения её текущих компонентов.

```cpp
// Добавить один или несколько компонентов сразу:
world.AddComponents(e.getEntity(), Health{50.f}, Damage{15.f});

// Перезаписать на месте, если компонент уже есть:
world.AddComponents(e.getEntity(), Health{25.f});

// Удалить типы компонентов:
world.RemoveComponents<Damage>(e.getEntity());
```

Замечания:

- Добавление уже существующего компонента **перезаписывает** его (move-assign из
  rvalue, copy-assign из lvalue).
- Удаление типа, которого у сущности нет, игнорируется.
- Удаление **последнего** компонента уничтожает сущность — сущность на архетипах
  не может существовать без компонентов.
- Все эти операции — no-op для мёртвой сущности.

> **Делаете это посреди кадра?** Менять архетипы во время итерации `view`
> небезопасно. Лучше откладывайте структурные правки [командами](./commands.md),
> которые выполняются между кадрами.

## Типизированные обёртки

Для более богатого API над фиксированным набором компонентов наследуйте обёртку
от `EntityWrapper` (она не должна добавлять **никаких** полей — всё состояние
живёт в компонентах):

```cpp
struct Player final : ecs::EntityWrapper
{
    using EntityWrapper::EntityWrapper;

    float GetHealth() const         { return GetComponent<Health>().value; }
    void  SetHealth(float v)        { GetComponent<Health>().value = v; }
    Position2d& GetPosition()       { return GetComponent<Position2d>(); }
};

// Попросите Create вернуть ваш тип обёртки:
Player player = world.Create<Player>(std::move(prefab));
player.SetHealth(75.f);
```

Концепт `ecs::EntityWrapperLike` на этапе компиляции проверяет правило «никаких
лишних полей».
