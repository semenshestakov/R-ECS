# Джобы и многопоточность

[🇬🇧 English](../../en/guides/jobs.md) · [⬆ Документация (русский)](../README.md)

R-ECS не поставляет пул потоков и **не** привязан к какой-либо библиотеке задач.
Ядро зависит от единственного абстрактного порта — `ecs::IJobScheduler`, — а
конкретный бэкенд внедряется в рантайме. Это позволяет подключить TBB, пул на
`std::thread` или собственный планировщик, не трогая код ECS и систем.

## Порт

[`ecs/jobs/IJobScheduler.hpp`](../../../include/recs/ecs/jobs/IJobScheduler.hpp) —
единственная завязка ядра на многопоточность. Ни один заголовок из
`include/ecs` не включает потоковую библиотеку.

```cpp
class IJobScheduler
{
public:
    using RangeBody = FunctionRef<void(std::size_t first, std::size_t last)>;

    // Кадровая работа — стартует и джойнится внутри кадра.
    virtual void      ParallelFor(std::size_t begin, std::size_t end,
                                  std::size_t grain, RangeBody body) = 0;
    virtual JobHandle Run(std::function<void()> job)                 = 0;
    virtual void      Wait(const JobHandle& handle)                  = 0;
    virtual std::size_t WorkerCount() const                          = 0;

    // Сервисы — долгоживущая, внекадровая работа.
    virtual ServiceHandle SpawnService(std::function<void()> tick,
                                       ServiceDesc desc = {})        = 0;
    virtual void          StopService(const ServiceHandle& handle)   = 0;
    virtual void          PumpServices()                       { /*по умолчанию no-op*/ }
    virtual bool          CanHostDedicatedThreads() const noexcept { return false; }
};
```

Интерфейс **намеренно крупнозернистый**: каждый метод — точка входа уровня
система/кадр, поэтому единственный виртуальный вызов на запуск ничтожен на фоне
запускаемой работы. Поэлементная работа едет в `RangeBody` —
[`FunctionRef`](../../../include/recs/ecs/jobs/FunctionRef.hpp), невладеющая ссылка на
callable без аллокаций, — и выполняется без дополнительной косвенности.

Порт покрывает **две модели исполнения**. Первые четыре метода — *кадровая
работа*, которая стартует и джойнится внутри кадра. Остальные — *сервисы*:
долгоживущая работа, переживающая отдельный кадр (см.
[Сервисы](#сервисы-внекадровая-работа) ниже). `Run` возвращает
[`JobHandle`](../../../include/recs/ecs/jobs/JobHandle.hpp) — opaque value-тип. Ядро в
него не заглядывает: бэкенд кладёт за типобезопасное состояние всё, что ему нужно
(task group, future, latch), и приводит обратно в своём `Wait`.

## Дефолтный бэкенд

У каждого `Registry` всегда есть валидный, не-null планировщик. Если ничего не
установлено — используется
[`SerialJobScheduler`](../../../include/recs/ecs/jobs/SerialJobScheduler.hpp), который
выполняет всю работу синхронно в текущем потоке. Поэтому ядро полностью
работоспособно без бэкенда, а однопоточные сборки не платят ничего.

## Установка бэкенда

Внедри настоящий пул через `Registry::SetScheduler`. Код систем не меняется.

```cpp
auto registry = ecs::Registry::Create("game");
registry.SetScheduler(std::make_unique<MyTbbScheduler>(/*потоков*/ 8));
registry.Init();
```

Передача `nullptr` сбрасывает к серийному бэкенду — реестр никогда не держит
null-планировщик.

## Как написать бэкенд

Реализуй кадровые методы, затем сервисы. `Run` ставит задачу и возвращает хэндл,
состояние которого сигналится по завершении; `Wait` его джойнит. `ParallelFor`
бьёт `[begin, end)` на чанки не меньше `grain` и применяет `body` к каждому,
возможно параллельно, блокируясь до завершения всех. `body` обязан быть безопасен
для параллельного выполнения на непересекающихся под-диапазонах.

```cpp
class MyTbbScheduler final : public ecs::IJobScheduler
{
    void ParallelFor(std::size_t begin, std::size_t end,
                     std::size_t grain, RangeBody body) override
    {
        tbb::parallel_for(
            tbb::blocked_range<std::size_t>(begin, end, grain),
            [&](const tbb::blocked_range<std::size_t>& r) { body(r.begin(), r.end()); });
    }
    // Run / Wait / WorkerCount ...

    // Пул крутит tick-цикл сервиса на воркере, поэтому PumpServices остаётся
    // дефолтным no-op. CanHostDedicatedThreads может вернуть true, если бэкенд
    // умеет ещё и прибить сервис к собственному OS-потоку.
    ServiceHandle SpawnService(std::function<void()> tick, ServiceDesc) override
    {
        auto source = ecs::StopSource::Active();
        auto token  = source.token();
        auto state  = launch_worker([token, tick = std::move(tick)] {
            while (!token.stop_requested()) tick();          // циклом владеет бэкенд
        });
        return ecs::ServiceHandle{std::move(source), std::move(state)};
    }
    void StopService(const ecs::ServiceHandle& h) override
    {
        h.request_stop();          // затем джойн воркера за h.state()
    }
};
```

Бэкенд живёт в **своём** таргете и линкует TBB; ядро ECS собирается и тестируется
без него. Это обычная инверсия зависимостей: ядро зависит от порта, бэкенд — и от
ядра, и от своей потоковой библиотеки.

## Параллельный запуск систем

`SystemsManager::Update` диспатчит каждую **стадию** расписания через
`Registry::Scheduler().ParallelFor`. Стадия — это набор систем без рёбер порядка
между ними, то есть ровно те системы, которые безопасно запускать одновременно,
поэтому их вызовы `Update` отдаются планировщику и могут выполняться сразу на
нескольких воркерах. Так как `ParallelFor` блокируется до конца стадии, конец
каждой стадии — неявный барьер, и стадия *N+1* (которая может зависеть от *N*)
стартует только после полного завершения стадии *N*. С дефолтным
`SerialJobScheduler` всё по-прежнему выполняется инлайн, так что поведение не
меняется, пока не установлен реальный бэкенд.

Это покадровая («кадровая») работа: стадия стартует и завершается внутри того
`Update`, который её запустил.

## Сервисы — внекадровая работа

**Сервис** — это долгоживущая работа, переживающая отдельный кадр (пул сети,
стриминг ассетов, фоновый микшер), которая тикает, пока её не остановят или пока
не умрёт реестр. Заводится через тот же порт:

```cpp
auto svc = registry.Scheduler().SpawnService(
    [] { stream_one_chunk(); },           // один короткий возобновляемый шаг
    { .name = "asset-streaming" });
// ... позже, или никогда (реестр сам остановит на teardown):
registry.Scheduler().StopService(svc);
```

Три свойства делают сервисы портируемыми и безопасными:

**Тик, а не цикл.** `SpawnService` принимает один короткий возобновляемый шаг, а
не собственный `while`-цикл. Циклом владеет *планировщик* и проверяет отмену
между тиками. Именно это позволяет беспоточному
[`SerialJobScheduler`](../../../include/recs/ecs/jobs/SerialJobScheduler.hpp)
соблюсти тот же контракт: он хранит сервис и тикает его раз за вызов
`PumpServices()` — который `Registry::Update` зовёт каждый кадр, — так что на
серийном бэкенде сервис деградирует до кооперативного тика в главном потоке, ровно
как `ParallelFor` деградирует до инлайн-цикла. Реальный пул вместо этого крутит
`while (!stop) tick();` на воркере и оставляет `PumpServices` пустым. Держи тики
короткими, чтобы отмена оставалась отзывчивой.

**Кооперативная отмена.** `SpawnService` возвращает
[`ServiceHandle`](../../../include/recs/ecs/jobs/ServiceHandle.hpp) с
[`StopSource`](../../../include/recs/ecs/jobs/StopToken.hpp); сервис наблюдает
парный read-only `StopToken`. `StopService` запрашивает стоп и джойнит (на
серийном бэкенде джойн — no-op: сервис просто отбрасывается на следующем пампе).

**Умирает вместе с реестром.** `Registry` владеет планировщиком через
`unique_ptr`, а планировщик владеет своими сервисами. Когда реестр умирает,
деструктор планировщика останавливает и освобождает каждый сервис — ни один не
переживёт мир, который кормит. `SetScheduler(nullptr)` так же сносит старый бэкенд
со всеми его сервисами перед установкой серийного.

Настоящие **выделенные OS-потоки** — для жёсткого реального времени (аудио) или
блокирующего сокет-I/O, где кооперативного тика мало, — это *опциональная
возможность*, а не часть универсального контракта. Бэкенд объявляет её через
`CanHostDedicatedThreads()` (по умолчанию `false`); серийный бэкенд их не даёт.
Кооперативные сервисы, напротив, обязан соблюдать любой бэкенд.

Сервис не должен трогать состояние ECS напрямую (то же правило, что для рабочих
потоков ниже): направляй структурные изменения через
[очередь команд](./commands.md), а общие данные читай через `ctx().get<T>()`. Для
высокочастотной передачи предпочитай lock-free буфер, который сервис наполняет, а
главный поток вычитывает, вместо мьютексной очереди команд.

## Правила многопоточности

Бэкенды обязаны быть безопасны для вызова из главного потока; безопасность из
рабочих потоков определяется бэкендом. Как и везде в R-ECS, **структурные
изменения** (создание/удаление сущностей, добавление/удаление компонентов,
регистрация систем) не должны происходить из рабочих потоков — направляй их
через отложенную [очередь команд](./commands.md), которая сбрасывается в главном
потоке. Чтение и запись значений компонентов у непересекающихся сущностей
параллельно — безопасны.

В debug-сборках эти правила проверяются. Приложение само назначает свой главный
поток, один раз вызвав `ecs::MarkMainThread()` на старте (это политика
приложения, а не `Registry`) — например, в начале `main`, до создания реестра и
запуска цикла кадра. После этого структурные / однопоточные точки входа через
`ECS_ASSERT_MAIN_THREAD` проверяют, что вызов идёт именно из этого потока:

- сущности — `EntitiesManager::Create` / `Destroy` / `AddComponents` / `RemoveComponents`;
- системы — `SystemsManager::Register` / `Enable` / `Disable`;
- события — `EventSystem::OnEvent` / `PushEvent` / `FlushEvents`;
- контекст — `Context::emplace` / `getOrEmplace` / `remove`.

Две смежные операции вместо ассерта сделаны **потокобезопасными by design**,
поэтому ограничения на главный поток у них нет:

- **Очередь команд.** `CommandQueue::Push` — канал деферрала для систем, его
  можно звать из любого потока: конкурентные пуши сериализуются внутренним
  мьютексом. Параллельная система кладёт сюда свои структурные изменения, а
  выполняются они на потоке `Registry` при следующем `Flush()`, который берёт тот
  же мьютекс лишь на время свапа очереди, а затем исполняет команды без лока (так
  он не гонится с конкурентным `Push`, не держит лок на пользовательском коде, и
  команда может сама сделать `Push` без дедлока).
- **Регистрация компонентов.** `ComponentRegistrator::Register` выполняется
  лениво при первом достижении `GetComponentId<T>()` — а это может быть глубоко
  внутри итерации `view<...>`. Magic-static на тип ограничивает это «один раз на
  тип», а мьютекс сериализует параллельную регистрацию *разных* типов — так что
  безопасно даже при первом обращении из параллели. Регистрация редка; прогрев
  компонентов на главном потоке на старте просто избавляет от лока на горячем
  пути.

Вызов гардованной операции из воркера — например, прямое изменение сущностей
внутри параллельной системы вместо постановки команды — роняет assert. Пока
`ecs::MarkMainThread()`
не вызван, проверки неактивны (рапортуют успех), поэтому забытый вызов никогда не
даёт ложного срабатывания — лишь пропуск проверки. Под `NDEBUG` проверка
компилируется в ноль, так что release не платит ничего.

Собственные раннеры тестов и бенчмарков R-ECS вызывают `ecs::MarkMainThread()` в
самом начале `main`, так что проверки активны на протяжении всего прогона.

`ecs::Context` — тонкий адаптер слоя ecs над обобщённым `collections::Context`
(так же как `ecs::EventSystem` оборачивает обобщённый диспетчер событий): он
гардит только мутирующие операции, а чтение `get` / `has` наследуется без
изменений и остаётся безопасным для конкурентного вызова из воркеров на уже
существующих записях. Создавай общие ресурсы в главном потоке, затем читай их
через `get<T>()` из параллельных систем.
